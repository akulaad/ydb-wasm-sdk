# Настройка кластера и загрузка WASM UDF

WASM UDF — пользовательская функция, скомпилированная в WebAssembly и доступная
из SQL-запросов YDB. Эта инструкция показывает, как включить поддержку WASM на
существующем кластере, загрузить пример `Hello` из SDK и вызвать его из запроса.

Для исполнения примера нужны два артефакта: библиотека `sdk` с общими функциями
runtime и модуль `Hello`. Они загружаются в UDF Store — хранилище модулей выбранной
базы данных. После загрузки сервер компилирует WASM для процессоров узлов базы.

## Перед началом

Подготовьте:

- Работающий кластер и базу данных YDB. Серверная сборка должна содержать UDF Store,
  UdfService и контроллер компиляции WASM. Наличие этих возможностей в произвольной
  стабильной версии не предполагается: согласуйте сборку с администратором.
- Учётную запись администратора для настройки кластера и операций UDF Store.
  Одних прав на выполнение SQL недостаточно для загрузки, просмотра и удаления
  модулей.
- Совместимый YDB CLI с командой `udf` или `experimental udf`. Может потребоваться
  experimental-сборка CLI. Способ проверки показан ниже.
- Checkout этого SDK, Linux x86_64 и Python 3.8+ для сборки примера и запуска
  helper. При первой сборке нужен доступ к сети для скачивания инструментов.

> Инструкция относится к экспериментальной реализации WASM UDF. Версия
> экспортированных исходников указана в [sdk.lock.json](../sdk.lock.json).
> Таблица совместимости SDK, runtime и серверных релизов ещё не опубликована.
> Согласуйте их версии до установки, особенно если в базе уже есть библиотека `sdk`.

## 1. Включите поддержку WASM на кластере

Этот шаг выполняет администратор. Если кластер уже настроен, перейдите к
[проверке подключения](#2-настройте-cli-и-проверьте-подключение).

Добавьте следующие параметры в действующую конфигурацию YDB:

```yaml
udf_store_config:
  enabled: true
  enable_wasm_udf: true
  kv_storage_media: ssd

feature_flags:
  enable_wasm_compile_controller: true

grpc_config:
  services_enabled:
    - udf
```

Это **фрагмент**, а не полный конфигурационный файл. В статическом YAML указанные
секции располагаются на верхнем уровне; в конфигурационном документе с обёрткой
`config` — внутри неё. Объедините их с существующими секциями, сохранив другие
параметры и элементы списков.

| Параметр | Назначение |
| --- | --- |
| `udf_store_config.enabled` | Включает UDF Store. |
| `udf_store_config.enable_wasm_udf` | Разрешает обработку WASM-модулей. |
| `udf_store_config.kv_storage_media` | Выбирает тип носителя для KV-хранилища UDF Store. Значение по умолчанию — `ssd`; для базы с HDD-хранилищем укажите `hdd`. Тип должен быть обеспечен конфигурацией хранилища базы. |
| `feature_flags.enable_wasm_compile_controller` | Включает создание контроллера, который назначает узлам задания компиляции. Без него загруженные модули не компилируются. |
| `grpc_config.services_enabled` | Дополнительно включает сервис `udf` на соответствующем gRPC endpoint. |

Если `udf` присутствует в `grpc_config.services_disabled`, исключите его из этого
списка: запрет имеет приоритет. Не заменяйте `grpc_config.services` списком из
одного `udf`, иначе можно отключить сервисы, необходимые для других операций.
Параметр `enable_unsafe_native_udf` для WASM не требуется.

Примените изменение способом, принятым для вашего развёртывания:

- [Управление конфигурацией YDB](https://ydb.tech/docs/ru/devops/configuration-management/).
- Для конфигурации V2: получите текущий документ через `ydb admin cluster config
  fetch`, внесите изменения и примените его через `ydb admin cluster config
  replace`. Подробности и ограничения описаны в [обзоре V2](https://ydb.tech/docs/ru/devops/configuration-management/configuration-v2/config-overview).

Проверьте применение настроек как на узлах управления кластером, так и на узлах
базы данных. Изменение набора gRPC-сервисов требует перезапуска соответствующих
серверных процессов; используйте штатный [rolling restart](https://ydb.tech/docs/ru/reference/ydbops/rolling-restart-scenario).
Проверяйте эффективную конфигурацию узлов в Embedded UI, а не только локальный
отредактированный файл. Для существующей базы дождитесь создания контроллера
компиляции после применения флага; его наличие проверяется среди системных
таблеток базы в Embedded UI (`WasmCompileController`).

Не создавайте и не удаляйте вручную служебные таблицы `.metadata/udf_store`:
их инициализацией управляет сервис.

## 2. Настройте CLI и проверьте подключение

Следующие команды выполняются в Bash из корня SDK. Выберите установленный CLI:

```bash
export YDB_BIN=ydb
```

Если experimental CLI установлен отдельно, задайте в `YDB_BIN` путь к его
исполняемому файлу. Наличие слова `experimental` в имени файла не требуется:
доступность команд определяется сборкой и проверяется через `--help`.

Используйте существующий профиль подключения или создайте его интерактивно:

```bash
export YDB_PROFILE=wasm-demo
"$YDB_BIN" config profile create "$YDB_PROFILE"
```

Укажите адрес endpoint **целевой базы**, путь базы и параметры аутентификации.
Если профиль `wasm-demo` уже существует, пропустите команду создания и используйте
его либо выберите другое имя. Профиль хранит параметры соединения; подробнее —
в [инструкции по профилям CLI](https://ydb.tech/docs/ru/reference/ydb-cli/profile/create).

Определите доступный префикс UDF-команд:

```bash
ydb_cli=("$YDB_BIN" --profile "$YDB_PROFILE")
if "${ydb_cli[@]}" udf upload --help >/dev/null 2>&1; then
    udf_cli=("${ydb_cli[@]}" udf)
elif "${ydb_cli[@]}" experimental udf upload --help >/dev/null 2>&1; then
    udf_cli=("${ydb_cli[@]}" experimental udf)
else
    echo 'CLI не поддерживает загрузку UDF; нужна совместимая сборка' >&2
    exit 1
fi
"${udf_cli[@]}" describe --help
"${udf_cli[@]}" list --format json
```

Последняя команда должна завершиться успешно; на новой базе список может быть
пустым. Это проверяет доступность сервиса и права пользователя, но ещё не
проверяет работу компилятора. Если команда завершается ошибкой, см.
[диагностику](#диагностика).

## 3. Соберите пример

Соберите runtime и пример из исходников SDK:

```bash
./ya make --build=release --target-platform=clang20-emscripten-wasm64 \
    ydb/udfs/wasm/sdk examples/hello
```

Получатся следующие файлы:

| Файл | Назначение |
| --- | --- |
| `ydb/udfs/wasm/sdk/libwasm-sdk.so` | Общая runtime-библиотека. |
| `examples/hello/libexamples-hello.so` | Модуль с функцией `Hello::hello`. |
| `examples/hello/manifest.json` | Имя, типы функций и зависимости модуля. |

Несмотря на расширение `.so`, бинарные файлы содержат WebAssembly. Результаты
сборки обычно являются символическими ссылками на кеш `ya`; при переносе на
другую машину копируйте содержимое файлов, например с помощью `cp -L`.

## 4. Загрузите библиотеку и модуль

Основной сценарий ниже использует [helper](../.agent/skills/ydb-udf-cli/scripts/upload_and_wait.py):
он вызывает CLI, загружает один артефакт и ждёт завершения компиляции. Это не
отдельный протокол загрузки, а автоматизация команд `upload` и `describe`.

### Библиотека runtime

Проверьте, существует ли библиотека `sdk`:

```bash
"${udf_cli[@]}" describe --name sdk --format json
```

Если она существует, проверьте совместимость с выбранным SDK, тип
`module.module_type: library`, вид `module.module_kind: wasm` и готовность
платформ. Готовность сама по себе не гарантирует совместимость ABI. Используйте
подходящую установленную библиотеку: обновление общей `sdk` влияет и на другие
модули базы. Ошибка доступа или соединения не означает, что библиотека отсутствует.

Если получен `NOT_FOUND` и библиотеку нужно установить, загрузите её с
[манифестом runtime](examples/sdk.manifest.json):

```bash
python3 .agent/skills/ydb-udf-cli/scripts/upload_and_wait.py \
    --profile "$YDB_PROFILE" \
    --file ydb/udfs/wasm/sdk/libwasm-sdk.so \
    --manifest docs/examples/sdk.manifest.json \
    --timeout 600 --command-timeout 180
```

Манифест задаёт имя `sdk`, тип `library` и вид `wasm`. Для библиотеки также нужен
`--manifest`: старые параметры загрузки `--kind library --name sdk` здесь не
используются. На создание и компиляцию runtime отведено до 600 секунд, на один
вызов CLI — до 180 секунд. При необходимости измените эти пределы под свой кластер.

### Модуль Hello

После готовности runtime загрузите пример:

```bash
python3 .agent/skills/ydb-udf-cli/scripts/upload_and_wait.py \
    --profile "$YDB_PROFILE" \
    --file examples/hello/libexamples-hello.so \
    --manifest examples/hello/manifest.json \
    --timeout 300
```

Helper автоматически выбирает `udf` или `experimental udf`. Он использует режим
`create-only`, чтобы не заменить существующий модуль с таким же именем.
Для другого модуля укажите его бинарный файл и манифест. Имя для команд `describe`
и SQL берётся из `module_name` манифеста, а не из имени бинарного файла.

Сообщение `Uploaded` содержит имя и UID — идентификатор загруженной ревизии.
Helper завершится успешно только после готовности этой же ревизии; окончательный
JSON `describe` выводится в stdout, сообщения о ходе выполнения — в stderr.
Зависимости автоматически не загружаются: для Hello библиотека `sdk` должна
быть подготовлена предыдущим шагом.

### Загрузка без helper

Если хотите управлять ожиданием самостоятельно, **вместо** вызова helper
выполните прямую команду CLI:

```bash
"${udf_cli[@]}" upload \
    --file examples/hello/libexamples-hello.so \
    --manifest examples/hello/manifest.json \
    --create-only --format json
"${udf_cli[@]}" describe --name Hello --format json
```

Сохраните `uid` из ответа `upload`. Повторяйте `describe` с интервалом около двух
секунд и ограничением времени ожидания. Успешная загрузка означает приём файла,
а не завершение компиляции. Правила интерпретации ответа приведены ниже.

## 5. Проверьте готовность и выполните запрос

В ответе `describe`:

- `module.uid` должен совпадать с UID загруженной ревизии. Другой UID означает,
  что модуль уже заменён другой загрузкой.
- `platforms` содержит состояния компиляции по `cpu_spec` — спецификации CPU
  серверных узлов. Массив должен быть непустым, а нужные платформы — иметь
  `status: ready`.
- `pending` и `compiling` означают ожидание или выполнение компиляции.
  При `failed` изучите `compile_error` соответствующей платформы.

По умолчанию helper ждёт готовности всех возвращённых платформ. Параметр
`--cpu-spec` позволяет явно выбрать платформу; его можно повторять. Используйте
его только если знаете спецификации всех узлов, на которых будет выполняться UDF.

После готовности выполните проверочный запрос. SQL-команда может иметь свой
experimental-префикс, поэтому определите его отдельно:

```bash
if "${ydb_cli[@]}" sql --help >/dev/null 2>&1; then
    sql_cli=("${ydb_cli[@]}" sql)
elif "${ydb_cli[@]}" experimental sql --help >/dev/null 2>&1; then
    sql_cli=("${ydb_cli[@]}" experimental sql)
else
    echo 'В выбранном CLI нет команды sql' >&2
    exit 1
fi
"${sql_cli[@]}" -s 'SELECT Hello::hello(42l) AS answer;'
```

Ожидаемое значение `answer` — `42`. Суффикс `l` задаёт целое типа `Int64`, который
ожидает функция. Если модуль ещё не найден сразу после `ready`, повторите запрос
через несколько секунд: узлам может потребоваться время на обновление метаданных.
Постоянная ошибка требует диагностики; повторная загрузка для этого не нужна.

## Обновление модуля и продолжение ожидания

Для намеренного обновления сначала получите текущий UID через `describe`, затем
передайте его как условие замены:

```bash
previous_uid='UID_ИЗ_DESCRIBE'
python3 .agent/skills/ydb-udf-cli/scripts/upload_and_wait.py \
    --profile "$YDB_PROFILE" \
    --file examples/hello/libexamples-hello.so \
    --manifest examples/hello/manifest.json \
    --replace-only --expected-uid "$previous_uid" --timeout 300
```

`--expected-uid` защищает от перезаписи чужого обновления между чтением и
загрузкой. После замены сервер выдаёт новый UID и заново компилирует модуль.

Если истекло только время ожидания, продолжите проверку той же ревизии:

```bash
uploaded_uid='UID_ИЗ_ОТВЕТА_UPLOAD'
python3 .agent/skills/ydb-udf-cli/scripts/upload_and_wait.py \
    --profile "$YDB_PROFILE" \
    --wait-only --name Hello --uid "$uploaded_uid" --timeout 300
```

Если таймаут произошёл во время самого `upload` и UID не получен, сначала
проверьте состояние через `describe`: сервер мог успеть принять файл.

## Использование с AI-ассистентом

В репозитории есть [навык `ydb-udf-cli`](../.agent/skills/ydb-udf-cli/SKILL.md)
с порядком загрузки, проверки зависимостей и ожидания компиляции. Передайте модели
этот файл как инструкцию; автоматическое обнаружение каталога `.agent/skills`
зависит от используемого клиента.

Пример запроса:

> Прочитай `.agent/skills/ydb-udf-cli/SKILL.md` и загрузи Hello через профиль
> `wasm-demo`. Проверь установленную библиотеку sdk, дождись компиляции и выполни
> проверочный SQL-запрос. Используй CLI из YDB_BIN.

Навык и helper не настраивают кластер и не устанавливают CLI. Передайте модели
имя существующего профиля; сами секреты в запрос добавлять не требуется.

## Диагностика

| Симптом | Что проверить |
| --- | --- |
| CLI не знает команду `udf` | Проверьте `experimental udf --help` и выбранный `YDB_BIN`. Возможно, нужна другая сборка CLI. |
| `UNIMPLEMENTED` / `CLIENT_CALL_UNIMPLEMENTED` | Убедитесь, что сервер содержит UdfService, сервис `udf` включён на используемом endpoint, а процессы перезапущены после изменения gRPC-конфигурации. |
| `FAILED_PRECONDITION`: WASM support is not enabled | Проверьте эффективные `udf_store_config.enabled` и `enable_wasm_udf` на узлах. |
| `UNAUTHORIZED` / Access denied | Проверьте профиль, аутентификацию и административные права. Права на SQL не заменяют права UDF Store. |
| Нет прогресса, `platforms` пуст или остаётся `pending` | Проверьте `enable_wasm_compile_controller`, наличие контроллера и работающих узлов базы; проверьте инициализацию UDF Store и доступность указанного `kv_storage_media`. |
| `failed` | Прочитайте `platforms[].compile_error`; проверьте совместимость бинарника, runtime и сервера, наличие нужных библиотек. |
| `ALREADY_EXISTS` | `create-only` обнаружил существующее имя. Для намеренного обновления используйте `replace-only` с текущим UID. |
| `ABORTED` / UID mismatch | Модуль изменился. Повторно выполните `describe` и определите, какую ревизию нужно использовать. |
| `ready`, но запрос не находит функцию | Проверьте базу подключения, `module_name` и имена функций в manifest; дайте узлам время обновить метаданные. |
