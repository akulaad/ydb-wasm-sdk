# Демо разработки и эксплуатации WASM UDF в YDB

Предлагаемый сюжет — проверка заказов по правилу скидок. За 20–25 минут
разработчик пишет C++ модуль в отдельном SDK, собирает WASM, загружает его
в работающую базу и вызывает из SQL. Затем показывает обработку некорректных
данных, диагностику исключения и обновление правила без пересборки сервера.

Это план показа. Прикладной модуль `OrderRules` предстоит написать при подготовке;
его контракт и ожидаемые результаты заданы ниже. Примеры `Hello`, `Md5`,
`BridgeTypes` и `Yexception` уже входят в SDK. Команды загрузки используют
существующий CLI и helper; весь сценарий ещё нужно прорепетировать на демобазе.

## Что увидит зритель

| Время | Действие | Наблюдаемый результат |
| --- | --- | --- |
| 0–2 мин | Показать SDK, исходники и исходный список модулей | Для разработки не нужен checkout сервера; видна библиотека runtime |
| 2–7 мин | Написать правило, разобрать ABI и manifest, собрать модуль | C++ превращается в WASM с объявленными SQL-типами |
| 7–10 мин | Загрузить модуль, открыть list и describe | Новый UID, manifest, зависимость sdk, компиляция по платформам |
| 10–13 мин | Обработать набор заказов SQL-запросом | Пользовательская логика работает внутри запроса |
| 13–18 мин | Показать перехват ошибки и неперехваченный yexception | NULL для плохой строки либо ошибка запроса с сообщением и гостевым стеком |
| 18–22 мин | Изменить правило и заменить модуль по UID | Новый UID и новый результат после компиляции |
| 22–25 мин | Повторить успешный запрос и показать каталог | База продолжает обслуживать запросы; при необходимости удалить демомодуль |

## Подготовка площадки

Использовать отдельную демобазу и административный профиль `wasm-demo`.
Настроить сервер, CLI и массивы Bash `ydb_cli`, `udf_cli`, `sql_cli` по
[инструкции подключения](getting-started.md#2-настройте-cli-и-проверьте-подключение).
Она учитывает оба варианта CLI: `udf` и `experimental udf`; SQL-префикс
определяется отдельно. Ниже команды выполняются из корня SDK в этой же Bash-сессии.

Перед показом:

1. Проверить совместимость сервера с закреплённой ревизией SDK. Для сообщения
   гостевого `yexception` сервер должен содержать обработку
   `__ydb_wasm_exception_message` из изменения YDB #54198.
2. Собрать runtime и примеры заранее, чтобы загрузка toolchain не заняла эфир.
   Живую сборку собственного небольшого модуля оставить в сценарии.
3. Установить подходящий runtime `sdk` по инструкции. Компиляцию runtime
   выполнить до показа. Если нужна демонстрация его установки с нуля,
   отвести отдельное время; длительность измерить на репетиции.
4. Подготовить исходники `OrderRules`, SQL и вторую версию правила. Для живого
   написания оставить тело одной функции; остальные файлы открыть готовыми.
5. Проверить весь сценарий на выбранной паре SDK/runtime/server. Сохранить
   вывод успешных запросов и ошибки как резерв для показа.

```bash
python3 tools/sdk/export.py --verify
python3 tools/sdk/smoke.py
"${udf_cli[@]}" list --format json
"${udf_cli[@]}" describe --name sdk --format json
```

Показать `sdk.lock.json`: исходная ревизия, профиль
`clang20-emscripten-wasm64`, цели экспорта. Объяснить, что `libwasm-sdk.so`
и модуль пользователя содержат WASM, несмотря на расширение `.so`.

## Написание модуля OrderRules

За основу взять `examples/hello`, новый каталог — `modules/order_rules`.
Показать три файла: `main.cpp`, `ya.make`, `manifest.json`.

Предлагаемый контракт:

| Функция | Типы | Поведение |
| --- | --- | --- |
| `Price` | `(Int64, Int64) -> Int64` | Сумма в копейках и скидка в процентах; ошибочный ввод завершает запрос |
| `TryPrice` | `(Int64, Int64) -> Optional<Int64>` | То же правило, но перехватывает `yexception` и возвращает NULL |

В первой версии допустима скидка от 0 до 30 процентов, сумма — от 0 до
1 000 000 000 копеек. Ограничение суммы исключает переполнение демонстрационного
выражения `amount * (100 - discount) / 100`; округление вниз явно входит
в контракт. При нарушении бросить `yexception` с конкретным сообщением,
например `discount must be in [0, 30], got 40`.

В `TryPrice` показать настоящий `try/catch (const yexception&)` внутри гостя.
В `Price` также перехватить ошибку и передать `e.what()` через существующий
`ThrowException`. Это даёт контролируемую ошибку SQL. Отдельный пример
`Yexception` ниже демонстрирует именно неперехваченный C++ throw через границу WASM.

На экране выделить:

- `BridgeGetInt64` для чтения аргументов и `MakeInt64(...).Release()` для результата.
- `MakeNull().Release()` для некорректной строки в `TryPrice`.
- `module_type: module`, `module_kind: wasm`, `module_name: OrderRules`,
  `module_extension: wasm`, `required_libraries: ["sdk"]` в manifest.
- Имена функций и SQL-типы в `functions`; если C++ exports называются иначе,
  задать поле `export` явно.
- `webassembly_udf.inc` и зависимость от гостевого ABI в `ya.make`.

```bash
./ya make --build=release --target-platform=clang20-emscripten-wasm64 \
    modules/order_rules
```

Ожидаемый файл при обычном `DLL()` —
`modules/order_rules/libmodules-order_rules.so`. Проверить имя на репетиции.

## Загрузка и каталог

Сначала выполнить прямую команду CLI, чтобы показать ответ загрузки:

```bash
"${udf_cli[@]}" upload \
    --file modules/order_rules/libmodules-order_rules.so \
    --manifest modules/order_rules/manifest.json \
    --create-only --format json
"${udf_cli[@]}" list --format json
"${udf_cli[@]}" describe --name OrderRules --format json
```

Скопировать выданный UID в `uploaded_uid` и продолжить ожидание через helper:

```bash
uploaded_uid='UID_ИЗ_UPLOAD'
python3 .agent/skills/ydb-udf-cli/scripts/upload_and_wait.py \
    --profile "$YDB_PROFILE" --wait-only \
    --name OrderRules --uid "$uploaded_uid" --timeout 300
```

Показать разницу: `list` — каталог, `describe` — manifest и состояния
компиляции в `platforms[]` по `cpu_spec`. Приём файла ещё не означает готовности
к вызову. Helper проверяет тот же UID и готовность всех возвращённых платформ;
пустой список платформ не считается успехом. Переходы `pending` и `compiling`
могут пройти слишком быстро для живого наблюдения — не обещать увидеть каждый.

## Выполнение правила из SQL

Сохранить запрос в `modules/order_rules/orders.sql`:

```sql
$orders = AsList(
    AsStruct(1l AS id, 10000l AS amount, 10l AS discount),
    AsStruct(2l AS id, 20000l AS amount, 25l AS discount),
    AsStruct(3l AS id, 10000l AS amount, 40l AS discount)
);
SELECT id, amount, discount,
       OrderRules::TryPrice(amount, discount) AS final_price
FROM AS_TABLE($orders)
ORDER BY id;
```

Запустить его через `"${sql_cli[@]}" -f modules/order_rules/orders.sql`.
В первой версии ожидаются `9000`, `15000`, `NULL`. Объяснить, что NULL получен
благодаря явному перехвату исключения в госте; движок не пропускает ошибочные
строки автоматически.

Для строгой функции выполнить отдельный запрос:

```bash
"${sql_cli[@]}" -s 'SELECT OrderRules::Price(10000l, 40l);'
```

Ожидается ошибка запроса с сообщением о допустимой скидке. Ненулевой exit code
здесь ожидаем; не объединять этот шаг с остальным показом под общим `set -e`.

## Неперехваченное исключение C++

Открыть готовый `ydb/udfs/wasm/yexception/main.cpp`. Показать цепочку
`fail → boom_middle → boom_leaf` и настоящий `ythrow yexception()`.
Модуль специально сохраняет отладочную информацию и запрещает inline.

```bash
python3 .agent/skills/ydb-udf-cli/scripts/upload_and_wait.py \
    --profile "$YDB_PROFILE" \
    --file ydb/udfs/wasm/yexception/libwasm-yexception.so \
    --manifest ydb/udfs/wasm/yexception/manifest.json --timeout 300
"${sql_cli[@]}" -s 'SELECT Yexception::fail();'
```

Ожидается ошибка запроса с `boom-yexception-from-wasm` и гостевым стеком.
Наличие конкретных имён кадров проверить на репетиции с выбранной сборкой.
Затем немедленно выполнить:

```bash
"${sql_cli[@]}" -s 'SELECT OrderRules::Price(10000l, 10l) AS final_price;'
```

Ожидается `9000`. Это проверка обслуживания следующего запроса после ошибки.

Текущий `__ydb_wasm_exception_message` в примере декодирует именно `yexception`
с учётом гостевого C++ ABI. Это не универсальная поддержка сообщений любых
типов исключений: нельзя обещать тот же результат для произвольного
`std::exception` или переносить декодер на другой runtime без проверки.

## Обновление правила

Во второй версии увеличить допустимую скидку с 30 до 50, обновив проверку
и текст диагностики. Пересобрать `modules/order_rules`, затем:

```bash
"${udf_cli[@]}" describe --name OrderRules --format json
previous_uid='ТЕКУЩИЙ_UID_ИЗ_DESCRIBE'
python3 .agent/skills/ydb-udf-cli/scripts/upload_and_wait.py \
    --profile "$YDB_PROFILE" \
    --file modules/order_rules/libmodules-order_rules.so \
    --manifest modules/order_rules/manifest.json \
    --replace-only --expected-uid "$previous_uid" --timeout 300
"${udf_cli[@]}" describe --name OrderRules --format json
"${sql_cli[@]}" -f modules/order_rules/orders.sql
```

Показать новый UID; третья строка теперь даёт `6000`. Сервер не пересобирается
и не перезапускается. Не обещать отсутствие задержки доступности при замене:
нужно дождаться компиляции и обновления метаданных узлов.

При наличии времени повторить замену со старым `previous_uid`: ожидается
`ABORTED`, защита от перезаписи чужого обновления. Для очистки получить актуальные
UID и удалить только созданные для показа `OrderRules` и `Yexception` командой
`delete --name ... --expected-uid ...`. Общую библиотеку `sdk` оставить.

## Дополнительные возможности и запасной сценарий

Если есть ещё 3–5 минут, загрузить уже собранные `Md5` и `BridgeTypes` через
тот же helper. На `Md5` показать использование contrib-библиотеки из SDK;
на `BridgeTypes` — контейнерные типы из его `query.sql`. Это отдельный блок,
который не удлиняет обязательную историю про разработку и эксплуатацию модуля.

Если прикладной модуль ещё не подготовлен, провести сокращённый показ на
`Hello`: написать тело `hello`, собрать, загрузить, выполнить
`SELECT Hello::hello(42l)`, затем показать `Yexception`. Такой показ покрывает
сборку SDK, загрузку, каталог и неперехваченное исключение; `try/catch` и
изменение бизнес-правила в нём отсутствуют.

## Критерии готовности демо

- SDK собирает runtime, Hello и Yexception; версии исходников зафиксированы.
- OrderRules проходит оба набора ожидаемых результатов на демобазе.
- `list` показывает загруженный модуль, `describe` — нужную ревизию и готовые платформы.
- TryPrice возвращает NULL на неверном вводе; Price и Yexception дают ожидаемые ошибки.
- После исключения проходит успешный запрос без перезапуска сервера.
- Замена выдаёт новый UID и меняет результат; устаревший UID блокирует замену.
- Время сборки, загрузки и ожидания измерено; подготовлены вывод и бинарники для резерва.
